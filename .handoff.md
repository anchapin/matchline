**#504 — flaky xfail fixed at the root cause.** It was not test ordering (`-p no:randomly`
did not help) and not hash randomisation (a fixed `PYTHONHASHSEED` did not help).
`_wall_direction_from_envelope` (`ifc_import.py:544`) matches a wall to an envelope edge
**by length alone**, taking the first edge within 0.1 m. The fixture's 10×8 room has two
10 m edges, and `ifc_export` writes the four walls in a nondeterministic set-derived order,
so the winner flipped `wall_dir` between `(+1,0)` and `(-1,0)`; only one put the
reconstructed opening point inside the space. The exported IFC was byte-identical in size
every run — the variance was entirely import-side.

Fixed by making the room a trapezoid with four distinct edge lengths (a rectangle can
never satisfy this, so the *shape* had to change, not the coordinates), plus
`strict=True`. **20/20 consecutive runs now report `1 xfailed`** (was 4 xpass / 8 xfail
per 12). The old xfail reason was wrong on both counts — the fixture is not "missing
IfcWalls" (there are four) and dedup does work in export — so it was corrected.

Added two stable tests: `test_export_dedups_identical_openings` asserts the export-side
dedup (2 openings → 1 `IfcOpeningElement`) directly on the file, as a non-xfail regression
test, since dedup is an export guarantee and should not be gated on the broken re-import
path; `test_envelope_wall_matching_is_length_only` pins the ambiguity so the trapezoid
workaround is not later mistaken for correctness.

**#505 filed** — the underlying production bug: length-only envelope matching is ambiguous
