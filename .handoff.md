**#505 fixed and closed (`3c94863`, CI success).** Two defects in the same block of
`_attach_openings_to_spaces`, fixed together because each masked the other:

1. `_wall_direction_from_envelope` matched a wall to an envelope edge on **length
   alone** (first edge within 0.1 m). Length is not an identity — every rectangle has
   two pairs of equal edges — so the winner depended on `model.envelope` ordering,
   and `ifc_export` writes walls in a nondeterministic set-derived order. Now matched
   **by position**: an edge qualifies only if an endpoint coincides with the wall's
   placement, which is exactly how `_read_bim_elements` builds envelope edges from
   walls (`ifc_import.py:835`, `p0 = (cx, cy)`). Length only breaks ties between
   edges sharing an endpoint. The direction is oriented to start at the wall's
   placement, so the sign is geometric, not export-order dependent. Genuinely
   ambiguous cases return `None` rather than guessing.
2. **Not in the filed issue, found while reproducing.** The projection subtracted
   `length_m / 2` from `s_center_m`, but `s_center_m` is measured from the wall's
   own origin along its local X axis — `_read_opening` validates it against
   `0 <= s <= length_m` (`ifc_import.py:974`) — and `BimElement.placement_m` *is*
   that origin. Every opening was displaced by half a wall. On the 12 m edge of the
   #504 fixture: `c + d*(s - L/2)` → **(17.2, 0) outside**, `c + d*s` → **(11.2, 0)
   inside**. This one is worse than the ambiguity: it hits **every** wall, not only
   rectangles. The ambiguity only chose which wrong side it landed on; the offset
   guaranteed it landed wrong.

An undeterminable wall direction now leaves openings unattached and raises a new
`opening_attachment` review item (added to both `ReviewItem.kind` and
`flag_for_review`'s `Literal`) — nothing is silently accepted, and the old code could
not represent this case because it always produced a direction, however unfounded.
